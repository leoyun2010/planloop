> 이 문서는 QA(사람 또는 Claude)가 그대로 실행할 수 있는 검증 절차다.
> 커버리지 기준: 모든 P0 요구사항(REQ)에 TC 1개 이상, 모든 정책(POL)에 위반 케이스 TC 1개 이상.

## 0. 이 문서를 쓰는 법

- **TC는 세 갈래로 도출했다.** ① REQ의 인수 조건 → 정상 케이스, ② POL의 「위반 시 처리」 → 예외 케이스, ③ 화면의 상태 4종과 입력 유효성 → 경계 케이스.
- **기대 결과의 「」 안 문구는 원문 그대로다.** 화면에 다른 문구가 나오면 문구가 틀린 것이 아니라 **정책 위반**으로 판정한다. 문구를 바꾸려면 `/change`로 POL을 먼저 고친다.
- **상태가 「보류」인 TC 9건은 아직 실행하지 않는다.** 근거 REQ·POL이 보류·미확정이라 기대 결과가 확정되지 않았다. 해당 오픈 이슈가 닫히면 상태를 「미실행」으로 바꾼다.
- **목업으로 먼저 확인할 수 있다.** `04-screens/`의 HTML 목업은 각 화면의 「동작 확인」 바에 이 TC의 절차와 같은 시나리오를 넣어 두었다. 개발 전에도 절차와 기대 결과를 눈으로 대조할 수 있다.
- 실행 결과는 상태 열에 기록한다: 미실행 / 통과 / 실패 / 보류.

## 1. 사용자 접수 흐름 (SCR-001 ~ SCR-006)

### TC-001 접수 기간 내 개인 신청 완료

- **목적**: 접수 시작~마감 사이에 참여자 1명이 6단계를 끝까지 통과해 신청이 저장되는지 검증한다.
- **유형**: 정상
- **사전 조건**: 집회 상태 「운영 중」, 접수 시작 일시 < 현재 < 접수 마감 일시, 온라인 접수 인원 < 1,320명, 개인정보 처리방침 본문 등록됨
- **절차**:
  1. SCR-001 접수 홈에 진입한다.
  2. [신청하기]를 누른다.
  3. SCR-002에서 이름 「홍길동」, 휴대폰 「01012345678」, 지역 「서울」, 성별 「남」, 참가 구분 「참여자」를 입력하고 [다음]을 누른다.
  4. SCR-004에서 구원 여부·마음 상태·건강 상태를 선택하고, 숙소 사용 여부 「숙소 사용」, 특이사항 「없음」을 입력한 뒤 [다음]을 누른다.
  5. SCR-005에서 개인정보 수집·이용 동의와 민감정보 수집·이용 동의를 모두 체크하고 [신청 완료]를 누른다.
- **기대 결과**: SCR-006 신청 완료 화면으로 이동한다. 참가비 「80,000원」, 입금 계좌, 입금자명 안내가 표시된다. 등록번호 자리에는 「미발급」이 표시된다. 관리자 SCR-015 명단에 해당 건이 상태 「미매칭」으로 나타난다.
- **관련**: REQ-001, REQ-003, REQ-004, REQ-005, REQ-008, REQ-009, REQ-010, REQ-011 / POL-045 / SCR-001, SCR-002, SCR-004, SCR-005, SCR-006

### TC-002 인도자 신청 시 동행자 단계 분기

- **목적**: 참가 구분을 「인도자」로 고르면 동행자 추가 단계가 삽입되고 총 인원·금액이 재계산되는지 검증한다.
- **유형**: 정상
- **사전 조건**: TC-001과 같음
- **절차**:
  1. SCR-002에서 참가 구분을 「인도자」로 선택하고 [다음]을 누른다.
  2. SCR-003에서 [+ 동행자 추가]로 2명을 입력하고 저장한다.
  3. [다음]을 누른다.
  4. SCR-004에서 3명분(본인 + 동행 2명)의 상태 입력을 순서대로 완료한다.
  5. SCR-005에서 동의 2종을 체크하고 [신청 완료]를 누른다.
- **기대 결과**: 3단계에서 합계 영역이 「총 3명 · 240,000원」으로 표시된다. SCR-004의 진행 표시가 1/3 → 2/3 → 3/3으로 넘어가고 앞 인원의 입력값은 유지된다. SCR-006에 「80,000원 × 3 = 240,000원」과 「대표(인도자) 한 분이 한 번에 입금하셔도 됩니다.」가 표시된다.
- **관련**: REQ-005, REQ-006, REQ-008, REQ-011 / POL-042 / SCR-002, SCR-003, SCR-004, SCR-006

- **기대 결과**: [신청하기]가 비활성 상태이고 「접수는 {시작일시}부터 시작합니다.」가 표시된다. 하단 탭의 공지·셔틀·마이페이지는 눌리며 각각 SCR-009, SCR-010, SCR-007로 이동한다.

### TC-023 참가비·계좌·입금자명 안내 표시

- **목적**: 완료 화면의 금액·계좌가 집회 설정값과 같은지 검증한다.
- **유형**: 정상
- **사전 조건**: SCR-014에서 참가비 80,000원과 입금 계좌가 저장된 상태. TC-001 완료 직후
- **절차**:
  1. SCR-006 신청 완료 화면의 참가비·계좌·입금자명 안내를 확인한다.
  2. SCR-014 집회 설정의 참가비·계좌 값과 대조한다.
- **기대 결과**: 두 값이 일치한다. 입금자명은 신청자 이름(인도자 신청이면 인도자 이름)으로 안내된다.
- **관련**: REQ-011, REQ-073 / POL-046 / SCR-006, SCR-014

### TC-024 입금 확인 소요 안내 상시 노출 검사

- **목적**: 입금 확인까지 2~3일이 걸린다는 안내가 두 화면에 항상 노출되는지 검증한다. 노출되지 않으면 정책 위반이다.
- **유형**: 예외
- **사전 조건**: 신청 1건 완료, 입금 미확인 상태
- **절차**:
  1. SCR-006 신청 완료 화면을 확인한다.
  2. SCR-007에서 본인 확인 후 SCR-008 마이페이지의 입금 상태 영역 바로 아래를 확인한다.
- **기대 결과**: 두 화면 모두에 「입금 확인까지 2~3일 정도 걸릴 수 있습니다. 입금하셨다면 조금만 기다려 주세요.」가 노출된다. 입금이 확인된 뒤에는 같은 위치에 확인 완료 표시가 대신 노출된다.
- **관련**: REQ-011, REQ-013 / POL-007 / SCR-006, SCR-008

### TC-025 암호화 대상 항목 평문 저장 차단·HTTPS 강제

- **목적**: 지정된 항목이 암호화되어 저장되고 모든 통신이 HTTPS로 이뤄지는지 검증한다.
- **유형**: 예외
- **사전 조건**: 개발·스테이징 DB 조회 권한. 신청 1건 저장 완료
- **절차**:
  1. `http://`로 접수 홈에 접근한다.
  2. 저장된 신청 건의 휴대폰 번호·건강 상세·구원 여부·마음 상태·숙소 특이사항 컬럼을 DB에서 직접 조회한다.
  3. 이름·지역 컬럼도 함께 조회한다.
  4. 암호화 대상 컬럼에 평문을 직접 기록하는 저장 요청을 시도한다.
- **기대 결과**: 1번은 `https://`로 리다이렉트된다. 2번의 값은 평문으로 읽히지 않는다. 3번의 이름·지역은 평문이고, 휴대폰에는 검색용 해시 컬럼이 별도로 존재한다. 4번은 저장이 실패하고 오류가 기록된다.
- **관련**: REQ-008, REQ-010 / POL-041 / SCR-004, SCR-005

### TC-026 보관기간 경과 개인정보 경고 표시

- **목적**: 보관기간이 지난 데이터가 남아 있으면 관리자에게 파기 필요를 알리는지 검증한다.
- **유형**: 예외
- **사전 조건**: 집회 상태가 「종료」로 바뀐 시점이 1년 이전인 개인정보 5건, 3개월 이전인 민감정보 3건이 남아 있는 상태
- **절차**:
  1. SCR-013 통합 대시보드에 진입한다.
  2. 파기 배치를 실행한다.
  3. SCR-025 변경 이력을 조회한다.
- **기대 결과**: 대시보드에 「보관기간이 지난 개인정보 {n}건이 있습니다. 파기가 필요합니다.」가 표시된다. 배치 실행 후 해당 데이터가 사라지고, 대상 건수·일시·실행자가 변경 이력에 기록된다.
- **관련**: REQ-010 / POL-039 / SCR-013, SCR-025
## 2. 본인 확인·마이페이지 (SCR-007, SCR-008)

### TC-027 휴대폰 + 이름으로 본인 확인 성공

- **기대 결과**: 조회 중 상태에서 「확인하는 중입니다…」가 표시된 뒤 SCR-008 마이페이지로 이동한다. 비밀번호 입력 단계가 없다.

### TC-028 본인 확인 불일치 차단

- **목적**: 일치하는 신청이 없을 때 차단 문구가 뜨고 입력값이 유지되는지 검증한다.
- **유형**: 예외
- **사전 조건**: 휴대폰 「01000000000」으로 신청된 건이 없음
- **절차**:

### TC-029 본인 확인 시도 제한 초과 차단

- **목적**: 동일 IP에서 10분간 10회를 넘겨 조회하면 10분간 차단되는지 검증한다.
- **유형**: 경계
- **사전 조건**: 같은 IP에서 최근 10분 내 본인 확인 조회 이력 0건
- **절차**:
  1. SCR-007에서 임의의 값으로 조회를 10회 연속 실행한다.
  2. 11회째 조회를 실행한다.
  3. 관리자 SCR-015 명단 검색을 실행한다.
- **기대 결과**: 10회까지는 불일치 문구가 뜨고, 11회째부터 [내 신청 확인하기]가 비활성이 되며 「조회 시도가 너무 많습니다. 10분 후에 다시 시도해 주세요. 급하시면 본부 접수처(연락처)로 문의해 주세요.」와 남은 시간이 표시된다. 차단 사실이 서버 로그에 기록된다. 3번의 관리자 명단 검색은 제한 없이 동작한다.
- **관련**: REQ-012 / POL-040 / SCR-007, SCR-015

### TC-030 마이페이지 상태 통합 조회

- **목적**: 등록번호·입금·숙소·셔틀·상담 상태가 한 화면에 모이는지 검증한다.
- **유형**: 정상
- **사전 조건**: 입금 매칭 완료, 숙소 배정 완료, 셔틀 배차 확정, 상담 배치 확정된 신청 1건

  2. SCR-008의 각 상태 영역을 확인한다.
- **기대 결과**: 등록번호가 발급값으로, 입금이 「확인」으로, 숙소가 구역·방·좌석으로, 셔틀이 확정 시간·차량으로, 상담이 일시·상담실로 표시된다.

### TC-031 입금 확인 전 등록번호 미발급 표시

- **관련**: REQ-034 / POL-038 / SCR-006, SCR-008, SCR-015

### TC-032 부분 매칭 상태 표시

- **사전 조건**: 총 3명 동행 신청 중 2명만 매칭 완료

- **기대 결과**: 입금 상태가 「부분 매칭」으로 표시되고 「함께 신청하신 분 중 2명의 입금이 확인되었습니다.」가 노출된다. 취소 버튼 노출 여부는 조회한 본인의 개인 단위 입금 여부로 판단된다.

### TC-033 숙소 배정 전 안내 문구 노출

- **사전 조건**: 입금 매칭 완료, 숙소 미배정
- **절차**:
  1. SCR-008 마이페이지의 숙소 영역을 확인한다.
- **기대 결과**: 「숙소는 집회 1~2일 전에 일괄 배정됩니다. 배정되면 이 화면에서 확인하실 수 있습니다.」가 표시된다.
- **관련**: REQ-013 / POL-014 / SCR-008

### TC-034 입금 확인 후 본인 취소 차단 [보류]

- **목적**: 입금이 확인된 뒤에는 참가자가 스스로 취소할 수 없고 관리자 연락처가 노출되는지 검증한다.
- **유형**: 예외
- **사전 조건**: 입금 매칭 완료된 신청 1건. **취소 권한 정책이 검토중(POL-004, REQ-014 보류) — 확정 후 실행한다.**
- **절차**:
  1. 입금 미확인 상태의 신청으로 SCR-008에 진입해 취소 영역을 확인한다.
  2. 입금 확인된 신청으로 SCR-008에 진입해 취소 영역을 확인한다.
  3. 2번 상태에서 취소 API를 직접 호출한다.
- **기대 결과**: 1번은 [신청 취소하기]가 노출되고, 누르면 「신청을 취소하시겠습니까? 취소하시면 되돌릴 수 없고 다시 신청하셔야 합니다.」 확인 절차를 거친다. 2번은 취소 버튼이 사라지고 본부 연락처만 표시된다. 3번은 「입금이 확인된 신청은 본인이 취소할 수 없습니다. 본부 접수처(연락처)로 연락해 주세요.」로 차단된다.
- **관련**: REQ-014 / POL-004 / SCR-008

## 3. 사용자 조회 화면 (SCR-009 ~ SCR-012)

### TC-035 공지·일정 조회

- **관련**: REQ-015 / POL-046 / SCR-009

### TC-036 비게시 항목 미노출·빈 상태 문구

- **목적**: 관리자가 비게시로 둔 항목이 사용자 화면에 나타나지 않고, 노출 대상이 없어도 빈 화면이 되지 않는지 검증한다.
- **유형**: 예외
- **사전 조건**: 공지 1건이 비게시 상태, 다른 게시 공지 0건, 오늘 일정 0건, 표시 안내문 0건
- **절차**:
  1. SCR-023에서 공지 1건을 비게시로 바꾼다.
  2. SCR-009를 새로고침한다.
  3. SCR-012 안내문 보관함에 진입한다.
  4. SCR-009에서 사용자 계정으로 공지 수정·삭제 요청을 시도한다.
- **기대 결과**: 비게시 공지가 목록에 없다. SCR-009에 「아직 등록된 공지가 없습니다.」와 「오늘 등록된 일정이 없습니다.」가, SCR-012에 「아직 등록된 안내문이 없습니다.」가 표시된다. 4번의 수정·삭제 요청은 차단된다.
- **관련**: REQ-015, REQ-016 / POL-046 / SCR-009, SCR-012, SCR-023

### TC-037 안내문 보관함 상시 재열람

- **목적**: 참가비·성경책·숙소 위치·FAQ 안내를 접수 마감 이후에도 열람할 수 있는지 검증한다.
- **유형**: 정상
- **사전 조건**: 표시 상태 안내문 4건 등록. 현재 시각 > 접수 마감 일시
- **절차**:
  1. SCR-012에 진입한다.
  2. 각 아코디언 항목을 펼친다.
- **기대 결과**: 4건이 모두 열람되고 첫 항목이 펼쳐진 상태로 진입한다. 접수 마감 이후에도 목록과 본문이 그대로 열리고 잠금 표시가 붙지 않는다.
- **관련**: REQ-016 / POL-046, POL-001 / SCR-012

### TC-038 셔틀 정기편 조회와 수시 요청 등록

- **목적**: 정기편 시간표 조회와 수시 요청 등록이 되는지 검증한다.
- **유형**: 정상
- **사전 조건**: 정기 운행 3건 등록됨
- **절차**:
  1. SCR-010에 진입해 정기편 시간표를 확인한다.
  2. 수시 요청에서 방향 「나가는 편」, 구분 「참여자」, 희망 시각을 입력하고 [요청하기]를 누른다.
- **기대 결과**: 정기편 3건이 시간순으로 표시된다. 요청 후 내 요청 영역에 「대기」 배지와 「본부에서 배차를 확정하면 여기에 시간과 차량이 표시됩니다.」가 나타나고, 관리자 SCR-022의 「나가는 편」 탭에 해당 요청이 나타난다.

### TC-039 셔틀 방향 미선택 차단

## 4. 집회 설정·통합 대시보드 (SCR-013, SCR-014)

### TC-046 집회 생성·상태 전환·과거 기록 조회

### TC-048 현장 버퍼가 총 정원 이상일 때 저장 차단

### TC-050 통합 대시보드 핵심 지표 표시

## 5. 접수·환불 관리 (SCR-015)

### TC-056 마감 이후에도 현장 수동 접수 가능

- **목적**: 접수 마감이 관리자 수동 접수를 막지 않는지 검증한다.

- **기대 결과**: 「이 자리에는 B 님이 배정되어 있습니다. 두 분의 자리를 서로 바꾸시겠습니까?」가 표시되고, 확인하면 A와 B의 좌석이 서로 바뀐다. 취소하면 아무것도 바뀌지 않는다.
- **관련**: REQ-046 / POL-018 / SCR-018

### TC-119 상담사별 타임라인 조회와 지연 표시

### TC-124 타임라인에 예약 격자를 두지 않음

- **사전 조건**: SCR-019, SCR-020, SCR-021 진입

  3. 같은 상담 1건을 SCR-021에서 시간 변경한 뒤 SCR-020에서 확인한다.
- **기대 결과**: SCR-020은 상담사 × 시간 축이고 상담실 예약 격자를 두지 않는다. SCR-021이 상담실·상담사·시간 배치를 담당한다. 3번의 변경이 SCR-020에 그대로 반영된다 — 배정 데이터가 한 곳에만 저장된다.

### TC-125 같은 상담사·같은 시간 이중 배치 차단

### TC-126 상담 지표와 상담실 실시간 상태

### TC-147 계정 발급과 역할 지정, 역할별 기본 권한

- **목적**: 전체 어드민이 계정을 발급하고 역할에 따라 기본 권한이 적용되는지 검증한다.
- **유형**: 정상
- **사전 조건**: 전체 어드민 로그인
- **절차**:
  1. SCR-024에서 [+ 계정 추가]로 역할 「본부 팀원」 계정을 발급한다.
  2. 그 계정으로 로그인해 사이드 내비를 확인한다.
  3. 역할 「셔틀팀」 계정을 발급하고 같은 방식으로 확인한다.
  4. SCR-024 계정 목록을 확인한다.
- **기대 결과**: 본부 팀원 계정은 계정 관리를 제외한 전체 메뉴가 열린다. 셔틀팀 계정은 셔틀 관리만 열린다. 계정 목록에 아이디·역할·소속·발급일이 조회된다.
- **관련**: REQ-066, REQ-067 / POL-030, POL-031, POL-032 / SCR-024

### TC-148 전체 어드민이 아닌 계정의 계정 관리 접근 차단

- **목적**: 계정 추가·권한 변경이 전체 어드민에게만 허용되는지 검증한다.
- **유형**: 예외
- **사전 조건**: 역할 「본부 총괄」 계정으로 로그인
- **절차**:
  1. SCR-024 URL로 직접 접근한다.
  2. 계정 추가 API를 직접 호출한다.
  3. SCR-025 변경 이력을 전체 어드민 계정으로 조회한다.
- **기대 결과**: 화면 진입이 차단되고 「계정 추가와 권한 변경은 전체 관리자만 할 수 있습니다.」와 함께 대시보드로 이동한다. API 호출도 차단된다. 시도 사실이 변경 이력에 기록된다.
- **관련**: REQ-066 / POL-030 / SCR-013, SCR-024, SCR-025

### TC-149 마지막 전체 어드민 보호와 아이디 중복 차단

- **목적**: 전체 어드민이 0명이 되는 상황과 아이디 중복을 막는지 검증한다.
- **유형**: 예외
- **사전 조건**: 전체 어드민 계정이 1개뿐인 상태. 아이디 「admin」이 이미 존재
- **절차**:
  1. 그 전체 어드민 계정의 역할을 「본부 총괄」로 바꾸려 한다.
  2. 그 계정을 삭제하려 한다.
  3. 아이디 「admin」으로 계정을 추가하려 한다.
- **기대 결과**: 1·2번은 「마지막 전체 관리자 계정은 역할을 바꾸거나 삭제할 수 없습니다.」로 차단된다. 3번은 「이미 사용 중인 아이디입니다.」로 차단된다.
- **관련**: REQ-066 / POL-030 / SCR-024

### TC-150 셔틀팀 외 외부 팀 계정 발급 경고

- **목적**: 계정 미발급 대상에 계정을 만들 때 경고가 뜨고 기록이 남는지 검증한다.
- **유형**: 예외
- **사전 조건**: 전체 어드민 로그인
- **절차**:
  1. SCR-024에서 소속을 외부 팀(집회장 팀 등)으로 골라 계정을 추가한다.
  2. 경고에서 계속을 선택한다.
  3. SCR-025 변경 이력을 조회한다.
- **기대 결과**: 「외부 팀 계정은 셔틀팀만 발급하기로 정해져 있습니다. 그래도 발급하시겠습니까?」가 표시되고, 강행하면 발급되되 변경 이력에 기록된다.
- **관련**: REQ-066 / POL-032 / SCR-024, SCR-025

### TC-151 메뉴 접근 권한 설정과 URL 직접 접근 차단

- **목적**: 메뉴 단위 권한 체크가 화면 노출과 URL 접근 양쪽에 적용되는지 검증한다.
- **유형**: 예외
- **사전 조건**: 본부 팀원 계정 1개
- **절차**:
  1. 전체 어드민이 SCR-024에서 그 계정의 「숙소 배치도」 권한 체크를 해제하고 저장한다.
  2. 해당 계정으로 로그인해 사이드 내비를 확인한다.
  3. SCR-018 URL로 직접 접근한다.
- **기대 결과**: 사이드 내비에 숙소 배치도가 노출되지 않는다. URL 직접 접근 시 「이 메뉴에 접근할 권한이 없습니다.」와 함께 대시보드로 이동한다.
- **관련**: REQ-067 / POL-031 / SCR-013, SCR-018, SCR-024

### TC-152 변경 이력 기록

- **목적**: 접수·입금·환불·숙소·상담·셔틀·설정 변경이 변경 전후 값·사유·담당자·일시와 함께 기록되는지 검증한다.
- **유형**: 정상
- **사전 조건**: 각 영역에서 변경을 1건씩 수행할 수 있는 데이터
- **절차**:
  1. SCR-015에서 참가자 정보를 수정한다.
  2. SCR-016에서 매칭을 해제한다.
  3. SCR-018에서 좌석을 이동한다.
  4. SCR-022에서 배차를 취소한다.
  5. SCR-014에서 참가비를 변경한다.
  6. SCR-025에서 5건을 조회한다.
- **기대 결과**: 5건 모두 기록되고 각각 변경 전 값·변경 후 값·사유·담당자·일시가 남는다. 조회 동작은 기록되지 않는다.
- **관련**: REQ-068 / POL-033 / SCR-014, SCR-015, SCR-016, SCR-018, SCR-022, SCR-025

### TC-153 이력 기록 실패 시 원 처리도 취소, 이력 수정 불가

- **목적**: 기록 없는 변경이 생기지 않고 기록이 수정·삭제되지 않는지 검증한다.
- **유형**: 예외
- **사전 조건**: 이력 저장을 실패시킬 수 있는 테스트 환경
- **절차**:
  1. 이력 저장이 실패하도록 설정한 상태에서 SCR-015의 참가자 정보 수정을 실행한다.
  2. 수정 결과를 확인한다.
  3. SCR-025에서 기존 이력 1건을 수정·삭제 API로 시도한다.
- **기대 결과**: 「처리 기록에 실패해 작업을 취소했습니다. 다시 시도해 주세요.」가 표시되고 참가자 정보가 바뀌지 않는다. 3번의 수정·삭제는 모두 차단된다.
- **관련**: REQ-068 / POL-033 / SCR-015, SCR-025

### TC-154 변경 이력 조회·필터·건별 조회

- **목적**: 최신순 조회, 메뉴·담당자 필터, 검색, 건별 팝업이 동작하는지 검증한다.
- **유형**: 정상
- **사전 조건**: 이력 50건 이상, 담당자 2명 이상
- **절차**:
  1. SCR-025에 진입해 정렬 순서를 확인한다.
  2. 메뉴 필터를 「입금 매칭」으로 바꾼다.
  3. 담당자 필터를 적용한다.
  4. 이름 또는 등록번호로 검색한다.
  5. SCR-015에서 특정 건의 [이력 보기]를 눌러 팝업을 연다.
  6. 조건에 맞는 이력이 0건이 되도록 필터를 조합한다.
- **기대 결과**: 최신순으로 정렬된다. 각 필터와 검색이 결과를 좁힌다. 건별 팝업에 그 건의 기록만 표시된다. 6번에서 「조건에 맞는 변경 기록이 없습니다.」가 표시된다. 첫 화면이 2초 이내에 뜬다(NFR-002).
- **관련**: REQ-069 / POL-033 / SCR-015, SCR-025

### TC-155 명단 내보내기 실행 이력 기록 [보류]

- **목적**: 개인정보가 외부로 나가는 내보내기가 기록되는지 검증한다.
- **유형**: 정상
- **사전 조건**: **REQ-075 보류. 내보내기 범위·권한 미확정(OI-23) — 확정 후 실행한다.**
- **절차**:

  2. 내려받은 파일의 항목을 확인한다.
  3. SCR-025 변경 이력을 조회한다.
- **기대 결과**: 파일이 생성되고, 실행 일시·실행자·범위가 변경 이력에 기록된다. 암호화 대상 항목이 복호화되어 포함되므로 기록이 반드시 남는다.
- **관련**: REQ-075 / POL-033, POL-041 / SCR-019, SCR-025

## 13. 화면 상태 공통 (전 화면)

### TC-156 사용자 화면 로딩 상태

- **목적**: 조회 대기 중 빈 화면 대신 로딩 표시가 나오는지 검증한다.
- **유형**: 경계
- **사전 조건**: 네트워크를 3G 수준으로 제한할 수 있는 환경
- **절차**:
  1. SCR-001, SCR-008, SCR-009, SCR-010, SCR-011, SCR-012에 각각 진입한다.
  2. 데이터가 도착하기 전 화면을 확인한다.
  3. SCR-005에서 [신청 완료]를 누른 직후 버튼 상태를 확인한다.
  4. SCR-007에서 조회 실행 직후 버튼 상태를 확인한다.
- **기대 결과**: 1~2번의 여섯 화면 모두 스켈레톤 또는 로딩 표시가 나오고 빈 화면이 노출되지 않는다. 3번은 버튼이 비활성이 되고 「신청을 저장하는 중입니다…」가 표시되어 중복 제출이 막힌다. 4번은 「확인하는 중입니다…」가 표시된다.
- **관련**: REQ-003, REQ-010, REQ-012, REQ-013, REQ-015, REQ-016, REQ-017, REQ-019 / SCR-001, SCR-005, SCR-007, SCR-008, SCR-009, SCR-010, SCR-011, SCR-012

### TC-157 사용자 화면 에러 상태와 다시 시도

- **목적**: 조회 실패 시 지정 문구와 재시도 수단이 제공되는지 검증한다.
- **유형**: 예외
- **사전 조건**: 서버 응답을 실패로 만들 수 있는 환경
- **절차**:
  1. SCR-001, SCR-008, SCR-009, SCR-010, SCR-011, SCR-012에서 조회를 실패시킨다.
  2. 각 화면의 문구와 [다시 시도] 버튼을 확인한다.
  3. SCR-002에서 중복 검사만 실패시킨다.
  4. SCR-006에서 신청 결과 조회만 실패시킨다.
- **기대 결과**: 각 화면에 「집회 정보를 불러오지 못했습니다.」 / 「신청 정보를 불러오지 못했습니다.」 / 「공지를 불러오지 못했습니다.」 / 「셔틀 정보를 불러오지 못했습니다.」 / 「상담 정보를 불러오지 못했습니다.」 / 「안내문을 불러오지 못했습니다.」와 [다시 시도]가 표시된다. 3번은 신청을 막지 않고 「지금은 기존 신청 내역을 확인할 수 없습니다.」 토스트만 띄운 뒤 진행을 허용한다. 4번은 「신청 정보를 불러오지 못했습니다. 잠시 후 [내 신청 확인하기]로 확인해 주세요.」를 표시하고 재신청을 유도하지 않는다.
- **관련**: REQ-003, REQ-004, REQ-011, REQ-013, REQ-015, REQ-016, REQ-017, REQ-019 / SCR-001, SCR-002, SCR-006, SCR-008, SCR-009, SCR-010, SCR-011, SCR-012

### TC-158 관리자 화면 빈 상태 문구

- **목적**: 데이터가 0건일 때 모든 관리자 화면에 다음 행동을 알려주는 문구가 나오는지 검증한다.

  2. 각 화면의 빈 상태 문구를 확인한다.
- **기대 결과**: 빈 화면이 하나도 없다. 각각 「운영 중인 집회가 없습니다.」 / 「아직 만든 집회가 없습니다.」 / 「아직 접수된 신청이 없습니다.」 / 「아직 업로드한 입금 내역이 없습니다. 은행에서 내려받은 엑셀을 올려 주세요.」 / 「출력할 명찰이 없습니다. 입금이 확인된 건만 대기열에 올라옵니다.」 / 「아직 배치도가 없습니다. 위에서 구역과 방을 입력해 만들어 주세요.」 / 「오늘 진행된 상담이 없습니다.」 / 「이 날짜에 등록된 상담사가 없습니다.」 / 「배치할 상담이 없습니다. …」 / 「이 방향으로 들어온 요청이 없습니다.」 / 「등록된 공지가 없습니다.」 / 「아직 기록된 변경이 없습니다.」가 표시되고, 가능한 곳에는 다음 행동 버튼이 함께 노출된다.
- **관련**: REQ-020, REQ-022, REQ-029, REQ-035, REQ-038, REQ-048, REQ-051, REQ-055, REQ-057, REQ-062, REQ-069, REQ-070 / SCR-013 ~ SCR-025

### TC-159 관리자 화면 로딩·에러 상태

- **목적**: 관리자 화면에서도 로딩·에러 처리가 일관되게 동작하는지 검증한다.
