# 구현 ↔ 기획 동기화 루프

개발이 진행되면 구현이 문서보다 앞서가는 일이 반드시 생긴다.
이때 **비교와 수정을 한 번에 하지 않는다.** 어느 쪽이 맞는지는 사람이 판단한다.

## 1단계: 비교 (이 단계에서는 어떤 문서도 수정하지 않는다)

1. 비교 대상을 확인한다: 구현 코드(파일/폴더 경로, diff, 또는 붙여넣은 코드)와 대조할 산출물 범위.
2. 관련 REQ/POL/SCR/TC를 찾아 구현과 대조한다.
3. 차이점만 테이블로 리포트한다:

   | # | 항목 | 문서 기준 (ID·인용) | 구현 기준 (파일·동작) | 차이 유형 |
   |---|---|---|---|---|

   - 차이 유형: 문서에 없는 구현 / 구현에 없는 문서 항목 / 값·조건 불일치 / 문구 불일치
4. 리포트 후 **멈추고** 항목별 판단을 요청한다: "문서가 맞음(구현 수정 필요)" vs "구현이 맞음(문서 갱신)".

## 2단계: 반영 (사용자 판단 후)

- **구현이 맞음 + 해당 문서가 승인 상태** → `/change`로 CR 생성 (출처: 개발) → 승인 → `/merge-change`
- **구현이 맞음 + 해당 문서가 초안/검토중** → 문서 직접 갱신 + 버전 올림 + 변경이력에 "구현 동기화" 기록
- **문서가 맞음** → 개발팀 전달용 요약을 작성한다: 수정할 파일/함수, 근거가 되는 POL/REQ 인용, 기대 동작
- 혼재하면 항목별로 위 세 경로를 각각 적용한다.

## 규칙

- 1단계에서 절대 문서를 고치지 않는다. "고치지 말고 비교만"이 이 스킬의 존재 이유다.
- 판단을 대신하지 않는다. 다만 각 항목에 참고 의견(어느 쪽이 합리적으로 보이는지와 근거)은 덧붙일 수 있다.
- 반영이 끝나면 `/plan-status`로 정합성을 확인한다.
