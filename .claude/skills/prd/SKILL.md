# PRD 작성/갱신

## 사전 조건

- `projects/<프로젝트명>/00-brief.md`가 있어야 한다. 없으면 `/plan-init`을 먼저 안내한다.
- 대상 프로젝트가 불명확하면 `projects/` 하위 폴더를 나열하고 사용자에게 확인한다.

## 절차

1. `00-brief.md`를 읽고, 기존 `01-prd.md`가 있으면 함께 읽는다.
2. 브리프의 핵심 기능을 기능 요구사항(REQ-###)으로 분해한다.
   - 기능 하나가 여러 화면·정책에 걸치면 검증 가능한 단위로 쪼갠다.
   - 각 REQ에 인수 조건(Acceptance Criteria)을 반드시 체크박스로 작성한다 — QA가 이 항목으로 테스트한다.
3. 불명확한 부분은 작성 전에 AskUserQuestion으로 확인한다. 특히:
   - 우선순위(P0/P1/P2) 판단이 갈리는 기능
   - 예외/에러 케이스 처리 방향
4. `templates/01-prd.md` 구조로 `projects/<프로젝트명>/01-prd.md`를 작성한다.
   - REQ 테이블의 "관련 정책/화면" 열은 아직 정책서·IA가 없으면 "TBD"로 두고, 이후 `/policy`, `/wireframe` 실행 시 채운다.
5. 비기능 요구사항(NFR)은 웹앱 기본 항목(성능, 보안, 브라우저 호환, 반응형, 접근성)을 제안하고 사용자와 확정한다.
6. **리스크**를 기록한다 — 특히 "봉인된 결정"(범위 제외, 보류로 못 박은 것)이 나중에 운영 압박으로 재론될 가능성을 리스크로 남긴다. 범위 논쟁이 생기면 이 문서로 되돌린다.
7. 완료 후 변경이력에 기록하고, 다음 단계로 `/policy`를 안내한다.

## 규칙

- 문서 상태가 "승인"인 PRD는 직접 수정하지 않는다 — `/change` 절차를 안내한다.
- ID는 재사용·변경 금지 (CLAUDE.md 참조).
- "빠르고 편리하게" 같은 검증 불가능한 표현을 쓰지 않는다. 수치·조건으로 쓴다.
