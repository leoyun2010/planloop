# 변경요청(CR) 작성

승인된 산출물은 직접 수정하지 않는다. 변경은 CR로 기록하고, 승인 후 `$merge-change`로 일괄 반영한다.
이 절차가 "개발/QA 중 요구사항 역반영"의 핵심이다.

## 절차

1. 사용자에게 변경의 배경을 확인한다: 무엇이 문제인가, 어디서 발견됐나(QA/개발/피드백), 얼마나 급한가.
2. **영향 분석**: 프로젝트의 모든 산출물에서 관련 항목을 찾는다.
   - `01-prd.md`, `02-policy.md`, `03-ia.md`, `04-screens/`에서 관련 REQ/POL/SCR ID를 grep으로 검색
   - 직접 언급된 것뿐 아니라 연쇄 영향(예: 정책 변경 → 그 정책을 인용하는 모든 화면정의서)까지 나열
3. `changes/open/`의 기존 CR 최대 번호 +1로 CR ID를 부여한다 (merged/도 확인해 번호 중복 방지).
4. `templates/change-request.md` 구조로 `changes/open/CR-###-<제목>.md`를 작성한다.
   - AS-IS는 현재 문서 내용을 그대로 인용한다 (추측 금지)
   - TO-BE에 신규 ID가 필요하면 초안 ID를 미리 부여한다
   - 반영 체크리스트에서 해당 없는 항목은 취소선 처리
5. 작성 후 사용자에게 CR 내용을 요약 보고하고 승인 여부를 묻는다.
   - 승인 시: CR 상태를 "승인"으로 바꾸고 `$merge-change` 실행을 안내(또는 바로 진행)
   - 기각 시: 상태를 "기각"으로 바꾸고 `changes/merged/`로 이동 (이력 보존)

## 규칙

- CR 하나에 하나의 논리적 변경만 담는다. 성격이 다른 변경은 CR을 나눈다.
- 영향 분석이 불완전한 채로 승인 요청하지 않는다 — 반영 시 문서 간 불일치가 생긴다.
